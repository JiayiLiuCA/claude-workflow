# 文档写作规则

读写 `docs/planning/`、功能目录下的 CLAUDE.md 或 `.claude/rules/` 时自动加载。

## 三条原则

1. **知识先放进代码，放不进的才写文档**：按下表从上往下放，越靠上越不会过期。签名、schema、路由清单、文件列表不写进文档，读代码。

   | 层 | 放什么 |
   |---|---|
   | 命名、类型、schema、enum | 数据形状、取值范围、约束 |
   | 测试，测试名描述行为 | 功能性行为与 edge case |
   | 代码旁的注释 | 故意为之、看起来像 bug 的写法的原因；会被其他功能调用的函数的契约 |
   | 域笔记 | 跨文件的行为、实测数据、否决过的方案、外部依赖改造点、已知缺陷 |
   | ARCHITECTURE | 系统地图、全局规则、局部规则的索引 |

   前三层的具体写法在各层代码规范 rules 的「注释与测试」一节。
2. **只写当前状态**：决定被推翻就直接改写成新结论，不留删除线和原文。推翻的过程与理由写进当时 step 文件的「实录」和 commit 正文，历史交给 git。
3. **写到会被读到的地方**：按下表把每条信息放到将来消费它的位置，后续 session 不翻历史就能拿到。

## 信息去处

| 信息 | 去处 | 谁读 |
|---|---|---|
| 用户可见的功能现状，产品语言，不写目录 | OVERVIEW「已有功能」 | 用户 |
| 全部 milestone 与未完成 step：目标、范围、状态 | OVERVIEW「路线图」 | 用户、plan、roadmap |
| 给某个后续 step 的提示与遗留问题 | OVERVIEW 路线图中该 step 的「前置提示」；尚未拆出的写进所属 milestone | plan、roadmap |
| 尚未决定的问题；还没验收的行为，写成「待验收」并带预期结果 | OVERVIEW「待决」 | 用户、plan |
| 已有功能的目录、技术职责、依赖 | ARCHITECTURE「系统地图」 | 每个 session 自动加载 |
| 涉及多个功能的规则：全局的 | ARCHITECTURE 架构规则「全局」 | 每个 session 自动加载 |
| 涉及多个功能的规则：能列出只约束哪几个功能的 | `.claude/rules/<规则名>.md`，ARCHITECTURE「只约束部分功能」留一行索引 | 读写 `paths` 里的文件时自动加载；新代码由 plan 点名 |
| 单个功能内放不进代码的知识：跨文件的行为、实测数据、否决过的方案、外部依赖改造点、已知缺陷 | 该功能的域笔记 | 读写该功能的文件时自动加载 |
| 技术选型与代码约定：语言与框架版本、主要库、命名、错误处理、测试写法 | `.claude/rules/<layer>.md` | 读写对应文件时自动加载 |
| 过程：偏离、临场决策、遗留、验收、推翻了什么、路线图为什么改 | step 文件「实录」与 commit 正文 | close 读 execute 的 commit 正文，之后是存档 |
| 给核对合并的人看的：用户能看到什么不同、和计划不一样的地方、验收、风险 | PR 正文，格式见 close-step 第七步 | 只给人看，后续阶段不读，不能是任何知识的唯一去处 |
| 代码能回答的 | 不写 | |

**决定三条件**：决定写进架构规则或域笔记，须同时满足：撤回代价大；不知道背景的人会觉得奇怪或想改掉；当时有真实的备选。缺一条就不写，代码自己能说明。

## ARCHITECTURE

每个 session 都加载，所以逐条按「每个 session 都要用吗」取舍，写得短而准；1 万字符（`wc -m`）只是报警线，不是写到这里为止。只写每个 session 都要用、又不能从代码和配置一眼看到的：概述、核心概念、核心约束、目录结构（一两句惯例）、系统地图、全局规则、局部规则的索引。技术栈写进各层代码规范，读到该层代码时加载；配置文件与目录树能看到的不抄。

- **核心概念**：只收本项目特有的领域名词，一两句定义；文件路径、字段名、枚举值不写。
- **核心约束**：只写会改变设计的硬约束；Claude 默认就会遵守的（如避免过度工程）不写。
- **系统地图**：每个功能一行。「目录」写功能目录；按层分的项目写一两个入口文件，完整文件在该功能域笔记的 `paths`（规则加载时去掉 frontmatter，要看完整列表须直接读该文件）。「负责」一句话；「依赖」只写功能名。函数名、参数、实现细节不写。
- **全局规则**：约束所有功能，或约束每个 step 都会写的代码（如状态写入、对外分数口径）。一条一行 `- **A编号 标题**：结论。理由。`，一到三句，编号不复用；不写 Step 编号、文件清单与实现细节。细节按谁要用放：落实这条规则的每个功能都要用的进层规范，只和一处代码有关的进代码注释，只和一个功能有关的进该功能的域笔记。
- **局部规则**：能列出只约束哪几个功能的。正文只写一份，放在 `.claude/rules/<规则名>.md`，`paths` 覆盖索引里列出的每个功能的目录或文件；各功能怎么落实（入口、例外）可以写在各自的域笔记，共用的约束不在两处写。索引行写编号、规则、约束的功能、正文文件；「规则」一列先写哪种代码受约束，再写结论，如「新增 LLM 调用：先过共享 server 的归属检查」；约束的功能写全。正文只在读写 `paths` 里的文件时加载，新代码（新功能、已有功能第一次做这类事、按层分项目的新文件）不在其中：plan 按索引判断新代码受哪几条约束，写进 Plan，并把新代码所在的文件或目录加进 `paths`、所属功能加进索引，close 按实际文件核对。
- 只约束一个功能的不是架构规则，写进该功能的域笔记。

## 域笔记

域的边界由目录结构决定，bootstrap 定一次，Claude 不在每个 step 重新判断。

- **功能目录就是域**：bootstrap 选定按功能分目录、功能内部再分层，写进 ARCHITECTURE「目录结构」。新功能由 plan 在「范围内」指定新目录，close 在「系统地图」加一行。每个功能目录一份 `CLAUDE.md`。
- **放置规则**：一条知识写进包含它涉及的全部代码的最低一级目录。那是某个功能目录，就写进它的 CLAUDE.md；涉及多个功能，按上一节分全局规则与局部规则。前端和后端各有功能目录时，行为写在实现它的那一侧，前端笔记只写 UI 特有的行为；前端依赖的后端约定（状态、错误前缀的含义）先写进两侧共用的类型或常量，放不进的在前端笔记也写一句结论。
- **只放一层**：读一个文件时，从根目录到该文件沿路每一级目录的 CLAUDE.md 都会加载，层数越多读得越多。笔记默认只放在功能目录。
- **按需创建**：第一次在该功能里产生放不进代码的知识时由 execute 创建，没有这类内容不建。
- **只写碰这个功能就要用的**：笔记读到该功能任一文件都会加载。只写跨文件的行为、有过取舍的决定与否决的方案、实测数据、踩坑、外部依赖改造点、已知缺陷（现状，留在笔记；要修的另按下面「打算做的事」记一条）。下面这些不写进笔记：
  - 只和一处代码有关的「为什么」：写成那段代码的注释，已有就不重复；close 不能改代码，注释里还没有的先留在笔记
  - 代码能看到的：常量值、键清单、公式、函数做了什么
  - 约束几个功能的规则：按「ARCHITECTURE」一节写成局部规则
  - 只在部分文件用到的：放到加载范围更窄的地方，如子目录的笔记；按层分的项目写进 `paths` 更窄的 rule 文件（前端特有的写 `<feature>-ui.md`，外部包改造点只挂包目录）。前后端都要用的约定按放置规则处理
  - 打算做的事：进目标 step 或所属 milestone 的「前置提示」，没有明确目标的进 OVERVIEW「待决」；还没验收的行为进「待决」，写成「待验收」并带预期结果
  - Step 编号；指向在同一场景下会自动加载的文件的指路（如同一功能的层规范）。「改这里要连带看另一个功能」是功能之间的关系，不算指路：留下，或写成局部规则
- **结构从简**：功能职责已在系统地图，不重复。按主题分节，空节不写：规则与决定、跨文件的行为、实测与踩坑、外部依赖改造点、已知缺陷。决定写成「结论。理由。」，用户拍板的写明；实测数字带测量条件。edge case 优先写成测试，笔记只写测试表达不了的部分。
- **报警线**：全文 8000 字符（`wc -m`，含 frontmatter），超了由 close 提醒精简，不是写到这里为止。
- **各阶段都可写**，hook 放行：execute 随代码更新，plan / close / hotfix 发现过期就地修正。

### 按层分目录的项目

已有项目按层分目录（`models/`、`services/`、`routers/` 各放所有功能）、或框架强制按层时，没有功能目录可放笔记。bootstrap 在 ARCHITECTURE「目录结构」注明后，域笔记改用 path-scoped rule：

- 每个功能一份 `.claude/rules/<feature>.md`，frontmatter 的 `paths` 列出该功能在各层的文件，读写其中任何一个时自动加载：

  ```markdown
  ---
  paths:
    - "backend/app/*/ocr*.py"
    - "frontend/src/pages/ocr/**"
  ---
  ```

- 内容标准、结构、放置规则与上面相同。
- hook 把 `.claude/rules/` 算作文档，execute 不能写：execute 把功能内的新知识写进 commit 正文「临场决策」段，由 close 写进这个文件，新功能由 close 新建。
- `paths` 不列出的文件读写时不加载：plan 定稿时把「范围内」给已有功能新增的文件加进其 `paths`，close 按 `git diff --stat` 的实际文件核对。

## 压缩

close 发现 ARCHITECTURE 超过 1 万字符、或本次碰过的域笔记与局部规则文件超过 8000 字符时，问用户是否顺带压缩。ARCHITECTURE 每个 session 都会加载，它的上限最要紧。

- 只允许四种操作：合并重复、删除已被代码或后续决定取代的条目、把历史叙述改写成当前状态、把规则移到更窄的加载范围。仍在生效的约束不许删，拿不准就保留。
- ARCHITECTURE 按顺序做，够了就停：
  1. 按「ARCHITECTURE」一节的写法改回：地图「负责」超过一句、规则超过三句、混进 Step 编号、文件清单或实现细节
  2. 全局规则里能列出只约束哪几个功能的改为局部规则，只约束一个功能的移进该功能的域笔记
  3. 合并同一主题的全局规则
  4. 删除新代码违反时也会被自动检查拦下的规则（lint、类型检查、扫描全部代码的测试）；只测现有功能的测试不算
- 域笔记与局部规则文件按「域笔记」一节的不写清单逐条删或挪；仍超再把子主题拆到更窄的加载范围。
- 保留的约束对其引用的代码位置做定点核对。
- 压缩完派一个不带本会话上下文的 subagent，对照改前版本逐条核对：挪走的在去处找得到，删掉的符合判据，局部规则的 `paths` 覆盖所列功能；不符合的补回后再核对。
- commit 正文列「删除与合并清单」，挪走的写明去处，每条一行写原因，留作追查记录；正确性由上一条的 subagent 把关，PR 的「✅ 验收」写一句核对结论。
- 压缩后仍超：用 AskUserQuestion 问用户是否提高报警线。

## 修改纪律

- 定点编辑，不整节重写（压缩除外），不建版本后缀文件。
- plan review 的结论（含口头调整）必须回写 step 文件的 Plan 节：execute 只认文件。
- step 文件在 close 追加实录后是存档，不再修改。
- OVERVIEW 与 PR 正文写给人看，用产品语言。ARCHITECTURE、域笔记、step 文件与 commit 正文写给后续 session 的 Claude，保持技术精确。
