你现在处于设计稿阶段：按产品说明出设计稿，写进 `docs/design-reference/`。bootstrap 在前端代码规范里指向这里，Step 0 把 `tokens.css` 接进样式代码，之后每个做界面的 plan / execute 按 README 的页面对照表读对应页面稿，execute 新增公用组件时更新这里的组件库。本阶段只写 `docs/design-reference/`（以及第一步回写 PRODUCT.md 的页面与流程），不写应用代码，不选前端框架。

**参数**：`$ARGUMENTS`（风格参考：喜欢的网站、截图、品牌色、形容词；为空则从对话取）。
**续接**（resume / compact 后或新会话接着做时重新调用）：看 `git log --oneline --grep='^Design:'` 与 `docs/design-reference/`。还没有 `Design: … 关键页` 的 commit → 从第三步接着，README 与 tokens.css 里已有的方向沿用；已有 → 从第四步接着，只做 PRODUCT「功能 / 第一版」涉及、`pages/` 下还没有文件的页面。

# 产出格式

所有文件双击就能在浏览器打开（`file://`），不需要安装或启动任何东西：

- 纯 HTML + CSS，不用框架、构建工具与 CSS 预处理器。不用 `<script type="module">`、`import`、`fetch()`，它们在 `file://` 下会失败。脚本只用于展示交互状态（弹窗打开、标签切换），写在页内。
- 样式用相对路径引用：`pages/` 下的页面写 `<link rel="stylesheet" href="../tokens.css">` 与 `../components.css`，根目录的 components.html 直接写 `tokens.css` 与 `components.css`。
- 网络字体用 `<link>` 引入，`font-family` 写完整的本地后备字体栈，断网时版式不乱。图标用内联 SVG，不引用图标库。
- 内容用产品说明里的真实名词和像样的示例数据，不写 lorem ipsum。
- 页面宽度按 PRODUCT「约束」的使用设备：手机与电脑都要支持的写成响应式，自查时两个宽度都看。

```text
docs/design-reference/
├── README.md                  # 设计原则、页面对照表、组件清单、未覆盖
├── tokens.css                 # 全部样式数值：:root 下的 CSS 变量
├── components.css             # 公用组件的样式，只引用 tokens.css 的变量
├── components.html            # 组件展示页：每个组件的变体与状态
└── pages/<feature>-<page>.html  # 一个页面一个文件，kebab-case 英文；<feature> 与 PRODUCT「功能」对应
```

- **tokens.css**：颜色（背景、表面、主次文字、主色、危险 / 成功 / 警告、边框）、字体族、字号阶梯、行高、字重、间距阶梯、圆角、阴影、动效时长。变量按用途命名（`--color-text-muted`），不按色值命名（`--gray-500`）。
- **components.css**：页面实际用到的公用组件，常见的有布局壳（导航、页头）、按钮、表单控件、表格或列表、弹窗、提示、状态与进度、空状态、错误状态。只引用 tokens.css 的变量，不写字面色值、字号与间距。
- **页面**：页面特有的样式写在页内 `<style>`，同样只用变量。页面之间按 PRODUCT「主要流程」用 `<a>` 互相链接，主要流程能一路点完。非正常状态（空数据、出错、加载中）在同一页用切换展示，或另起 `<feature>-<page>--<state>.html`。

README.md 模板：

~~~markdown
# 设计稿

页面双击即可在浏览器打开。Step 0 把 `tokens.css` 接进样式代码后两边同步维护：execute 新增公用组件、改组件的样子或样式数值时，在同一个提交里更新本目录；两边不一致时以代码为准。

|---|---|---|---|

## 组件

|---|---|---|
~~~

# 第一步：读取

1. `docs/brief/PRODUCT.md`：定位、用户与场景、核心名词、功能、约束里的使用设备、页面与流程。文件不存在：停下，提示先跑 `/product`；用户只想要设计稿时，请用户口头给出定位、第一版功能与页面清单。
2. 「页面与流程」缺失或不全：从「功能」推出页面清单与主要流程，回写 PRODUCT.md，并告诉用户补了哪些。不悄悄自造页面。
3. 用户给的风格参考。
4. 审美方向：Skill 列表里有 frontend-design 时先加载，只用它定配色、字体与整体方向。它面向营销单页（hero 等），应用界面以信息组织与操作效率为先，页面结构、产出格式与看稿节奏以本 skill 为准。没有时告诉用户可以用 `/plugin install frontend-design@claude-plugins-official` 安装后重新调用；用户不装也继续，按第二步自己定。

# 第二步：定方向

先定一份方向说明，不单独给用户看，第三步随关键页一起给。配色与字体直接写进 tokens.css，布局与原则写进 README「设计原则」，会话压缩后不丢：

- 配色：按用途命名的 4 到 6 个核心色，加状态色
- 字体：一到两个字体族及各自用途，字号阶梯
- 布局：导航方式（侧边栏 / 顶栏 / 无）、内容宽度、信息密度
- 原则：三到五条本产品特有的取舍

自查：把同类的另一个产品放进来，是不是也会得出这一套。是，说明它是默认值而不是为这个产品做的选择，按产品的用户、场景与核心名词改掉。用户给了风格参考的以参考为准。

# 第三步：关键页（第一次给用户看）

1. 选关键页：最常用的页面，和最复杂的页面（信息最多或操作最多）。是同一个就一页，否则两页。告诉用户选了哪几页、为什么。
2. 依次写 tokens.css → components.css（只做关键页用到的组件）→ 关键页。关键页至少画出一种非正常状态（空数据或出错），让用户看到真实的信息密度。配色、字体、组件都放在关键页里给用户看，不单独出色板。
3. 有浏览器工具（Playwright、Claude in Chrome 等）时打开截图自查：对齐、溢出、文字截断、对比度。截图放 scratchpad，不进 repo。Claude in Chrome 默认打不开 `file://`，要在扩展设置里打开「允许访问文件网址」；打不开就在 `docs/design-reference/` 下临时起 `python3 -m http.server` 看，看完关掉。
4. 给用户：文件路径（双击打开）、方向说明（配色、字体、布局、原则各一两句）、请用户重点判断的两三处（整体风格、信息密度、导航方式）。按意见改到用户确认。
5. 确认后补全 README（设计原则、页面对照表、组件），按 CLAUDE.md「Git 约定」commit `Design: <产品名>关键页（方向已定）`。

# 第四步：其余页面（第二次给用户看）

1. 范围：PRODUCT「功能 / 第一版」涉及的全部页面。「之后」的页面不画，写进 README「未覆盖」。
2. 先用已有组件。需要新组件时加进 components.css，不在页面里另写一套；改了已有组件，回头看一遍关键页。
3. 写 components.html：每个组件的变体与状态（默认、悬停、禁用、出错、加载）。
4. 自查（有浏览器工具时截图）：PRODUCT 第一版的每个功能都能在页面上找到入口；主要流程能从页面链接一路点完；不同页面上的同类元素长得一样；tokens.css 之外没有字面色值、字号与间距。
5. 更新 README 的页面对照表、组件与未覆盖。
6. 给用户：页面清单（按主要流程排序，附文件路径）、比关键页新增的组件、未覆盖的页面。按意见改到用户确认。

# 第五步：收尾

1. 用户确认后按 CLAUDE.md「Git 约定」commit `Design: <产品名>设计稿`。
2. 按 CLAUDE.md「沟通风格」的汇报顺序输出：结论一句；用户现在能打开看什么（入口：README 的页面对照表）；⚠️ 未覆盖的页面、PRODUCT「待定」里还影响设计的；👉 `/tech-stack`。
