你现在处于 **Step {N}** 的 Plan 阶段。不写代码，唯一产物是 step 文件的 Plan 节。

**参数**：N = `$step`（为空或不是数字则从触发语取）；`$ARGUMENTS` 去掉 N 后为本 step 的特殊关注点。
**续接**（resume / compact 后或新会话接着做时重新调用）：先看 `git status`、`git log --oneline -5` 与 step 文件判断做到哪一步，跳过已完成的，不重复建分支或 commit。

# 第零步：阶段标记与分支

1. 用 Bash 执行 `printf 'plan' > "$(git rev-parse --show-toplevel)/.claude/workflow-phase"`
2. 分支 `feat/step-{NN}-<slug>` 已存在（discuss 建过）则切过去。不存在则 `git fetch origin`，先核对上一个 step 已合入：`git show origin/main:docs/planning/OVERVIEW.md` 的路线图里 Step {N} 前面还有条目，说明上一个 step 的 PR 还没 merge 或顺序变了，停下问用户。核对通过后从 `origin/main` 创建（slug 为本 step 主题的 kebab-case 短词；无 origin 时核对与创建都用本地 main）

# 第一步：读取并复述

ARCHITECTURE 已随根 CLAUDE.md 自动加载，项目全局、系统地图与架构规则都在 context 里，不用再读。另外只读下面这些，定位读取，不通读：

1. OVERVIEW：路线图中 Step {N} 的条目（含前置提示；条目不存在 = 尚未登记）、「待决」中相关项
2. step 文件的「决议」节（如有）：plan 必须遵守
3. 相关代码：先用系统地图找到涉及的功能目录，再读其中的 model / migration / 路由 / 组件 / service。想了解既有行为先搜测试名。域笔记在读到对应功能的代码时自动加载；plan 要推翻其中的规则须在 Plan 里明写
4. 涉及前端时：design reference 对应文件

不读历史 step 文件：后续需要的信息 close 已写进路线图条目、域笔记和 ARCHITECTURE。读完用几句话复述：要做什么、相关的既有规则与前置提示、决议（如有）。

# 第二步：冲突检查

域笔记或 ARCHITECTURE 与实际代码不一致时**以代码为准**，就地修正文档（本阶段可写），在复述里说明。不要猜 schema，代码是终极 ground truth。

# 第三步：路线图对齐

Plan 的「目标」必须是路线图条目的细化，不得扩展：

- **一致**：进入第四步。
- **范围小于条目**（有意推迟）：推迟部分写进「范围外」并注明去向（哪个 step 或待定）。
- **超出条目或目标变了**：超出部分不进「范围内」，在总结里列为「路线图变更」交用户拍板；同意则先改路线图再定稿 plan，不同意则进「范围外」。
- **条目不存在**：先在路线图登记（编号接在最大编号之后，含「已完成」表），用户确认后再进第四步。

改路线图遵守 OVERVIEW「路线图」开头的规则，原因写进本阶段 commit 正文。

# 第四步：写 Plan 节

在 `docs/planning/STEPS/{NN}-<slug>.md` 末尾追加 Plan 节；文件不存在则创建，首行 `# Step {N}：<标题>`。已有 Plan 节（重跑 plan、execute 大偏离回来修订）则就地修改，不另起一节。

~~~markdown
## Plan

### 目标
用户能观察到的变化：「系统能做 X」，不是「实现了 Y 类」。

### 范围内
先写新代码放进哪个功能目录：沿用已有的，或为新功能开新目录（按层分的项目写明该功能在各层的文件）。再列颗粒度到大致新增 / 修改的文件、API endpoint、表 / 字段、页面 / 组件。

### 范围外
容易越界、容易被顺手做掉的部分，越具体越好：不实现某后续 step 的功能、不动某表、不重构某模块、不修某个已知的既有问题。

### 改动
按项目形态分层（前端 / 后端 / CLI / 外部依赖集成…）：新增或修改的模块、复用的已有部分、数据流变化。集成外部 package / repo 时写明来源、trim 范围、预计要改的地方。

### 接口契约
每个新增 / 修改的 API：method + path、请求与响应字段及类型、错误情况。只描述契约，不贴实现代码。没有写「无」。

### DB 变更
每个新增 / 修改的表：字段、类型、约束、索引、外键、migration 顺序。没有写「无」。

### 验收
每条标准一行，标明验证层级，覆盖可见行为、API、DB 与至少 1-2 条异常路径。默认 [自动]，写出测试名，execute 按名字逐条勾掉；测试框架、目录与跑法按 `.claude/rules/<layer>.md` 的测试约定。
- [自动] <行为>：<测试名>，<放哪 / 怎么跑>
- [实测] <行为>：Claude 用 e2e 框架的一次性脚本 / 浏览器 / curl / CLI 验证一次的步骤，产物不进 repo。只用于测试框架覆盖不到的集成点与实测数据；值得重复跑的写成 [自动]
- [手动] <行为>：为什么不能自动化。只允许两类：审美（视觉、动效、交互手感，用户把握；Claude 先截图）；本机无法复现的真实外部环境（真实硬件、第三方账号）

手动项为零是常态。功能性行为（点了之后发生什么、表单校验、路由、数据展示、错误呈现）必须是 [自动]，写成 [手动] 是 plan 的缺陷。

### 执行分段
仅在判定需分段时写。每段：**P{k}：<段标题>**，范围（负责的文件 / 模块 / 层）、前置（依赖上一段交付什么，P1 写「无」）、退出验收。退出验收格式同「验收」，但**只允许 [自动] 与 [实测]**：审美类 [手动] 统一放 step 级验收，段边界不需要用户介入，execute 过放行门就自行提交。末段的退出验收写「同验收」。

### 文档影响
close 的清单，没有写「无」：系统地图的变化（新功能、依赖变化）、要新增或改写的架构规则、新的代码约定、本 step 会决定的「待决」项、对后续 step 的影响。功能目录下的域笔记由 execute 随代码更新，不列在这里；按层分的项目列出要新建或更新的 `.claude/rules/<feature>.md`，由 close 写。

### 待确认
plan 的假设与需要用户回答的问题。review 后逐条回写进上面各节（接受的假设写进相关节）并清空本节。
~~~

**写作纪律**：描述行为与契约，不写实现代码（函数签名、伪代码、目录树除外）。篇幅以 execute 照着做、不用回头问为准，不凑篇幅。要写很长才讲得清，说明 step 过大，在总结里建议拆分。

**执行分段判定**（每个 plan 必做，结论写进总结）：估算 execute 能否在**一个 session 的 context** 内舒适完成。当前 effort：`${CLAUDE_EFFORT}`；effort 越高 thinking 占 context 越多，工具输出、测试与调试轮次同样计入，要留余量。

- **装得下就不分段**：分段有交接成本，不为分而分。
- **装不下就分段**，质量优先：宁可多分一段，不让任何一段在 context 将尽时赶工。沿依赖顺序切（如 P1 = migration + model + service，P2 = API + 前端），段间文件集尽量不相交；每段结束必须是可验证的完整状态（编译 / 类型检查通过、该段测试绿、不留半成品接口），下一段是全新 session，只能从 git commit 与 step 文件接手。常见 2-3 段，超过 4 段说明 step 过大，优先拆 step。
- 经验信号（满足其一即认真考虑）：预计新增 / 修改超过约 1000 行或 15 个以上文件；跨多个都需大量读现有代码的子系统；大规模机械改造与新逻辑混合。阈值按 200K context 校准，1M 窗口可放宽约 3 倍但仍质量优先；没有 auto compact 兜底的环境要更保守。
- **分段不等于拆 step**：分段解决「目标单一但工作量大」；目标发散的 plan 应拆 step，走路线图变更。

# 第五步：输出总结

按 CLAUDE.md「沟通风格」写给产品负责人看：

1. 做完这个 step，用户能做什么
2. 关键取舍：建议怎么选、对用户意味着什么
3. 路线图变更（如有）：超出条目的部分、建议是否纳入、对后续 step 的影响
4. 主要风险或不确定处
5. 一次做完还是分几次做：分段时一句话讲每段交付什么
6. 需要用户亲自看的东西：「验收」里的 [手动] 项，几条、各是什么；没有写「无」。段退出验收不该有
7. 需要用户拍板的问题（来自「待确认」）

# 第六步：review 与收尾

等用户 review。**所有 review 结论（含口头调整）回写进 Plan 节**，「待确认」清空：execute 只认文件。用户确认后：

1. 拍板了路线图变更：先改路线图
2. 路线图中 Step {N} 条目的状态改为「plan 已定稿」
3. commit：`Step {N} Plan: <标题>`（execute 中途大偏离回来修订时同样）
4. 用 Bash 执行 `rm -f "$(git rev-parse --show-toplevel)/.claude/workflow-phase"`
5. 提示下一步：单段 `/execute-step {N}`（大 step 建议新会话）；分段 `/execute-step {N} P1`，每段过放行门后 execute 自行提交并提示，用户**新开 session** 跑下一段
