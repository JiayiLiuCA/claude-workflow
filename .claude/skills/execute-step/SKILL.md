你现在处于 **Step {N}** 的 Execute 阶段。目标：严格按 step 文件写代码。

**参数**：N = `$step`（为空或不是数字则从触发语取）；`$segment` 形如 `P{k}` 时本次只执行该段，否则它属于补充说明；`$ARGUMENTS` 去掉 N 与段号后为补充说明。
**续接**（resume / compact 后或新会话接着做时重新调用）：先看 `git status`、`git log --oneline` 与对话摘要（如有）判断做到哪一步，跳过已完成的，不重复 commit。

# 第零步：阶段标记与分支

1. 用 Bash 执行 `printf 'execute' > "$(git rev-parse --show-toplevel)/.claude/workflow-phase"`
2. 确认当前在 `feat/step-{NN}-*` 分支上；`git stash list` 里有本 step 大偏离时暂存的代码（见第三步），问用户取回还是丢弃
3. **分段对齐**：查看 Plan 是否含「执行分段」小节，与参数核对：
   - 有分段、参数带 `P{k}`：k > 1 时先用 `git log --oneline` 确认 P1…P{k-1} 的 Execute commit 齐全，并快速重跑上一段的退出验收（至少编译 / 类型检查 + 相关测试绿）；缺段或验收不过，停下汇报
   - 有分段、参数未带段号：按 git log 推断下一个未执行的段，明确告知「本次执行 P{k}」后继续
   - 无分段、参数带段号：停下询问，不能自行发明段边界

# 核心原则

1. **按 Plan 的「范围内 / 范围外」严格约束自己**：没写的不做，明确说不做的绝对不做。
2. **Plan 没写清楚、且会影响用户可见行为或接口契约的细节，停下来问用户**（UI 交互、错误如何呈现给用户、契约字段的含义）；纯实现细节（内部命名、局部类型、代码组织）按既有代码与 `.claude/rules/` 的惯例决定，记进 commit 正文「临场决策」。
3. **Plan 与实际代码冲突，停下来问用户**，不要自己调和。
4. **不修改 `docs/planning/` 与 `.claude/rules/`**（hook 拦截）。唯一可写的文档是功能目录下的 CLAUDE.md 域笔记，见收尾第 1 步。
5. **按依赖顺序推进**：migration → model → service → API → 前端（按项目形态调整），每层写完先跑通再下一层，写一块测一块：验收里的 [自动] 项随该层代码写成测试，不留到最后补。
6. **分段执行时，本段之外一律视同「范围外」**：不提前实现后续段，不重构已交付段（Plan 明确要求的衔接改动除外）；段边界本身有问题时按「偏离」停下汇报。
7. **知识先放进代码**：代码只有 Claude 读，按 `.claude/rules/<layer>.md`「注释与测试」写：类型写全、名字表达意图；edge case 写成测试，测试名描述行为；故意为之、看起来像 bug 的写法写明原因；会被其他功能调用的函数写清契约。不写复述代码的注释。放不进代码的才进域笔记。

# 第一步：读取并复述

1. step 文件完整阅读（决议 + Plan）：复述「范围内」「范围外」「验收」；分段时另复述本段的范围、前置、退出验收与相邻段边界
2. 相关的现有代码：用已自动加载的 ARCHITECTURE「系统地图」定位功能目录。域笔记与 `.claude/rules/` 在读到对应代码时自动加载，不用单独读
3. 涉及前端时：design reference 对应文件

# 第二步：确认理解，再开工

写代码之前列出：Plan 中需要澄清的点、Plan 与现有代码的潜在冲突、执行顺序（按文件或模块分组）。有问题暂停等用户回答；没有则明确说「理解无歧义，开始执行」。

开工前把执行顺序建成任务清单（TaskCreate，一个阶段一个任务，末尾追加「验收自检」；会话里没有该工具就用文字列出）：这是给用户看的里程碑，不代表剩余时间。中途冒出的新工作先加进清单再动手。

# 第三步：按序执行

按第二步的顺序推进，在关键边界自检并简报，不停下等确认：migration 跑通、表结构正确；后端各层能 import、单测绿、API 实测正确；前端类型检查 / build 通过、页面加载不报错。

**必须停下汇报并等待指示的只有两类**：

1. **Plan 没写清、又影响用户可见行为或接口契约的细节**（核心原则 2）：用户答复后继续，答复记进 commit 正文「临场决策」。
2. **发现任何偏离 Plan 的事实**（字段类型不对、依赖的接口与预期不符、Plan 遗漏了必要改动、Plan 与代码冲突）：按用户裁决分流：

- **小偏离**（不动范围边界与契约本质：字段改名、必要的连带修改、实现细节调整）：继续执行，记入 commit 正文「偏离」。
- **大偏离**（方案更换、范围增减、契约 / schema 变化）：中止 execute。已写未 commit 的代码用 `git stash push -u -m "step-{NN} 大偏离：<偏离点>"` 暂存，工作树回到干净状态；清除阶段标记，由用户重开 `/plan-step {N}` 把修订写进 Plan、review 后再重新 execute，暂存的代码届时由用户决定取回还是丢弃。不允许带着「文件是方案 A、口头改成方案 B」的状态继续跑。

**大规模机械改造**（全量重命名、批量文案抽取、迁移适配）：拆成互不相交的文件集，用并行 subagent 分组执行（Agent 工具选 `fork` 类型，继承已读的 step 文件与代码），汇合后统一跑类型检查与测试。

# 第四步：验收自检与放行门

分段的非末段按本段「退出验收」自检，跑本段测试与编译 / 类型检查；单段与末段按 Plan「验收」自检，跑全量测试、类型检查与 build。

逐条核对，按层级输出 checklist：

- **[自动]**：对应测试存在且通过 → ✅（附测试名）。测试缺了先补，不拿实测顶替
- **[实测]**：Claude 自己验证一次 → ✅（附方式与结果）。实测是一次性验证，产物不进 repo：借 e2e 框架跑一次性脚本、浏览器工具、curl、CLI 都可以；但凡值得重复跑的就写成 [自动]。需要 app 跑着的，在后台起 dev server，验完关掉
- **[手动]**：审美项先截图存到 `.claude/verify/`（gitignored；e2e 框架直接存，浏览器工具截图 `save_to_disk` 后挪进去），列出路径与看什么 → ⚠️ 待用户确认；真实外部环境项 → ⚠️（附步骤）
- 任何一条做不到 → ❌（附原因）

Plan 用的是没标层级的旧格式，按同样规则自己归类：能写成测试的写成测试。

**放行门**，三条全满足才过：

1. 测试绿、类型检查 / build 通过
2. checklist 没有 ⚠️ 也没有 ❌
3. 没有偏离，或只有用户中途已裁决的小偏离（commit 正文照记）

过门：不等用户，直接做「收尾」自行 commit，再按第五步汇报。不过门：按第五步汇报，等用户验收通过后再做「收尾」。

diff 较大或触及核心逻辑时，在总结中建议用户在 close 前跑 `/code-review high origin/main...HEAD`（不自动跑；**不加 `--fix`**，它的修改在 checkpoint 之外且绕过下面的分流）。review 发现的问题按性质分流：

- **实现 bug**（绝大多数）：当场修复，追加 commit `Step {N} Execute: review fixes`，Plan 不动。
- **Plan 缺漏但不动范围与契约**：按小偏离处理。
- **动摇 Plan 决策**（契约 / schema / 方案不成立）：升级为大偏离。

# 第五步：汇报

**过门的段**：先输出固定两行：

```text
✅ P{k} 已提交：N 个测试通过，无需手动验证，无偏离
👉 下一步：新开 session 跑 /execute-step {N} P{k+1}
```

单段第一行写「Step {N} 已提交」；有已裁决的小偏离时「无偏离」改成「小偏离已记入 commit」。非末段到此为止；单段与末段第二行写 `/close-step {N}`，再接下面的完整汇报。
**未过门**：下面的完整汇报，等用户验收；非末段只覆盖本段。

按 CLAUDE.md「沟通风格」写给产品负责人看：

1. **现在能做什么了**：用户可见的功能与行为变化
2. **和 plan 说好的有什么不一样**：功能多了 / 少了 / 变了，各附一句为什么
3. **需要用户决定或确认的事**
4. **需要用户亲自看的东西**：checklist 里的 ⚠️ 项。审美项给截图路径、说看什么；真实外部环境项按操作步骤写。功能性行为不出现在这里，它们已由测试覆盖。没有写「无」
5. **遗留问题**：用产品语言

技术细节不进汇报，写进 commit 正文。过门后用户仍提出修改，当场改并追加 commit `Step {N} Execute: <子标题>`。

# 收尾（过门直接做；未过门等用户验收通过后做）

1. **更新域笔记**：本 step 碰过的功能里，有放不进代码、测试和注释、又仍约束后续工作的知识（功能内的决定，不论定在决议、Plan 还是执行现场；跨文件的行为、实测数据、踩坑、否决过的方案、外部依赖改造点），就写进该功能目录的 CLAUDE.md。决议与 Plan 里的决定也要写：step 文件 close 后是存档，后续 step 只能从这里读到。只写当前状态，决定写成「结论。理由（Step {N}）」，已有条目过期就改写。没有这类知识就不动。新建域笔记时先读 `.claude/rules/planning-docs.md` 的「域笔记」一节。
   两种知识 execute 不能直接写，写进 commit 正文「临场决策」段，由 close 写入：涉及多个功能的规则与功能间依赖的变化，进 ARCHITECTURE；按层分的项目（ARCHITECTURE「目录结构」注明域笔记用 rule 文件）的功能内知识，进 `.claude/rules/<feature>.md`。
2. commit：标题 `Step {N} Execute: <标题>`（分段时 `Step {N} Execute: <标题>（P{k}）`，P 标号专用于分段；单段内拆多个 commit 用 `Step {N} Execute: <子标题>`）。正文固定四段，close 直接取用，无内容写「无」：
   ```text
   偏离：与 plan 不同之处 + 原因
   临场决策：plan 没明确、现场决定的事 + 理由；另含要交给 close 写入的知识（涉及多个功能的规则，按层分项目的功能内知识）
   遗留：已知但本 step 不解决的问题，能判断的注明该由哪个 step 处理
   验收：是否过放行门；逐条结果（✅ / ⚠️ / ❌）+ 测试通过数（分段的非末段写本段退出验收）。未过门的，⚠️ 项按用户验收的结论改写后再 commit
   ```
3. 用 Bash 执行 `rm -f "$(git rev-parse --show-toplevel)/.claude/workflow-phase"`
4. 提示下一步：非末段 **新开 session** 跑 `/execute-step {N} P{k+1}`；单段或末段 `/close-step {N}`。过门的段这一句已在第五步的固定两行里，不重复

# 禁止事项

- 不修改历史 step 的代码（除非 Plan 明确要求）
- 不顺手引入 Plan 之外的依赖库
- 不添加 "for future use" 的代码
- 不把多个独立改动打包成一个「优化」
