你现在处于技术选型阶段：定下 bootstrap 需要的全部技术参数，写成 `docs/brief/TECH.md`。bootstrap 拿它写各层代码规范、CI、ARCHITECTURE 的初始架构规则与 Step 0 plan，不再问用户。本阶段只写 `docs/brief/TECH.md`，不写代码、不建项目、不装依赖。

**参数**：`$ARGUMENTS`（用户的技术偏好或限制；为空则从对话取）。
**续接**（resume / compact 后或新会话接着做时重新调用）：读已有的 TECH.md，还空着的节就是剩下的，从第二步对应的项接着做。

已有项目（仓库里已有应用代码）的技术栈以现状为准，不需要本阶段：告诉用户直接跑 `/bootstrap`。

# 第一步：读取

1. `docs/brief/PRODUCT.md`：约束（使用设备、离线、数据规模、性能、隐私、预算、已定的技术要求）、功能、页面与流程。文件不存在：停下，提示先跑 `/product`。
2. 有界面时读 `docs/design-reference/README.md` 与 `components.html`，看界面需要哪些能力：大表格、图表、拖拽、富文本、实时更新、动画。没有设计稿：提示可以先跑 `/design-draft`，用户要跳过就继续。

# 第二步：出方案

先自己把方案定全，再问用户。逐项给推荐、理由与考虑过的备选：

1. **形态与平台**：Web / 桌面 / CLI / 服务 / 库；目标操作系统与浏览器
2. **各层技术**：语言与版本、框架、主要库、数据库。库按第一步看出的界面能力与产品约束挑
3. **测试工具**：单元测试、接口测试；有界面时加组件测试与端到端测试。端到端框架须能截图，execute 的审美截图依赖它
4. **整体结构决定**：进程与通信模型、数据存在哪、离线与同步、鉴权方式这类形态级决定
5. **样式系统**（有设计稿时）：`tokens.css` 怎么接进来，如直接引入 CSS 变量、转成 Tailwind 主题
6. **部署与发布**：部署到哪、怎么发布、要不要自动更新
7. **开发方式**：一个人还是团队；main 是否受保护

事实自己查，不凭记忆：版本号查官方发布页或包仓库（`npm view <pkg> version`、PyPI 等），取当前稳定版；关键依赖是否支持目标平台、许可证是否允许预期用途、是否还在维护，查官方文档，需要时派 subagent 并行查。拿不准的重集成（OCR、本地模型、硬件、第三方 API）可以在 scratchpad 里做最小验证，产物不进 repo；本阶段验证不了的写进「待定」，注明在哪个 step 验证。

选型原则：主流、文档全、Claude 熟悉的组合优先；同等条件下依赖少的优先；不为将来可能的需求提前选重的方案。

# 第三步：问用户

只问会影响用户的：花钱的（付费服务、托管费用）、部署在哪、平台取舍（支持哪些系统）、用户或团队熟悉的语言（用户以后要自己看代码时）、以后换掉的难度。纯技术取舍按推荐定，理由写进 TECH.md，不问。

把问题建成任务清单（TaskCreate，一题一个；会话里没有该工具就用文字列出）。先用一两句讲方案全貌（做成什么、主要用什么），再分轮问：每轮只问前提已定的问题，用 AskUserQuestion 或对话，每题给推荐与备选，讲清对用户的影响（多花多少钱、少了什么能力、以后换掉要多大代价），不给只有实现差异的选项。每拍板一项当场写进 TECH.md。

# 第五步：收尾

1. 自查：bootstrap 第一步「技术」一组的每一项都有答案，或在「待定」里写明留到哪个 step；各层版本互相兼容；每一层都有测试工具；PRODUCT「约束」的每一条都有着落（满足它的选择，或写明不满足的原因）。
2. 按 CLAUDE.md「沟通风格」的汇报顺序输出：结论一句；用产品语言讲方案（做成什么、在哪里运行、有没有持续的费用、以后哪些地方换起来难）；⚠️ 留到以后再定或要在开发中验证的；👉 确认后提交，下一步跑 `/bootstrap`。
3. 用户确认后按 CLAUDE.md「Git 约定」commit `Tech: <产品名>技术方案`，再提示下一步。
